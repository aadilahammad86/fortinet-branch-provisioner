What exists now

Three deliverables, one shared engine.

A Windows application — FortiGate Branch Provisioner.exe. Five tabs: connect, networks, internet, filtering, apply. It validates settings before sending anything, previews changes as a dry run, applies them, then reads the whole configuration back and checks it. No Python installation needed on the engineer's laptop.

Command-line scripts — unchanged in purpose, rewritten to call the same engine. Used for head-office staging and scripted rollouts.

A shared engine — the fortigate/ package. The login and CSRF handling used to be copy-pasted into all nine scripts; now there is one copy. Both front ends apply byte-identical configuration, so a fix reaches both at once.

All three inside networks reach the internet through wan1 with NAT. Guest WiFi has that one rule and nothing else — the firewall's default deny is what keeps guests off the office LAN and Staff WiFi. That isolation is achieved by omission, which means it is also easy to destroy: adding a guest-to-inside rule silently removes it.

The 60F has no WiFi radio. "Staff WiFi" means a port an access point plugs into.

What the testing found

The unit was factory reset and rebuilt from scratch. Three real defects surfaced — none of which would have been visible without doing that.

Silent data loss

The firewall reports success on a write it partly ignored

Setting an IP on a port that still belonged to the built-in hardware switch returned success. The firewall applied the harmless fields — alias, role — and silently dropped the IP address. The script logged a tick and moved on.

On a real rollout that ships a half-configured firewall to a branch with clean logs saying it worked. Every interface write now reads the value back and fails loudly if it did not stick.

Blocked provisioning

A factory unit cannot be set up in one pass

A factory FortiGate puts the office LAN on 192.168.1.99. The Staff WiFi standard is 192.168.1.1 — the same range. The firewall refuses both, so the LAN has to move first, and moving it drops the connection doing the work.

Setup is therefore two passes with a reconnect between them. Both the app and the scripts now detect the clash up front and say so, rather than failing halfway through.

Latent

The LAN change had to be reordered to stay recoverable

Changing the LAN address and its DHCP range are two separate writes. If the address changed first and the DHCP write then failed, the firewall would hand out addresses on the dead subnet and nobody could reconnect without setting a static IP by hand.

DHCP is now written first, while the session is still alive. The address change is last and its lost reply is treated as the expected outcome.

Design consequence

Ports return to the hardware switch after a reset

A factory reset puts internal2–internal5 back inside the internal switch. Both front ends now break the target ports out automatically, so no manual step is needed on a new unit.

Two decisions worth revisiting

HTTPS deep inspection needs a certificate on every device

Deep inspection re-signs every secure connection. Until the FortiGate's certificate is installed on a device, that device cannot reach any secure site — not just the blocked ones. Major sites give no click-through option, so the firewall will look broken to the first person who opens a browser.

Certificate inspection blocks the same sites with no per-device setup. It is one radio button in the app. The trade is a plain browser error instead of a branded block page, and no ability to filter individual page paths later.

192.168.1.x for Staff WiFi is what forces the two-pass setup

It is also the most common home-router range, which will collide with staff working from home once the VPN is running. Moving Staff WiFi off 192.168.1.x — or adopting the planned per-branch 10.<branch>.x scheme — removes both problems and collapses setup back to a single pass.

Still open

  • VPN to head office — configured on-site per branch, not scripted. When it is added, give the tunnel to the office LAN and Staff WiFi only; never to Guest.
  • Unique subnets per branch — every branch currently gets identical ranges. They will collide over the VPN.
  • FortiGuard registration — all entitlements read pending. Site blocking is a fixed list and works offline; application blocking enforces on the firmware's built-in database but receives no updates until the unit is registered online.
  • Code signing — the app is unsigned, so Windows shows a security prompt on first run.
  • Admin password rotation — should be unique per branch unit.

On-site checklist

After a configured firewall reaches the branch.

  • Enter the ISP username and password on wan1, connect the internet cable. DNS configures itself.
  • Plug the Staff WiFi access point into internal2.
  • Plug the Guest WiFi access point into internal3.
  • If deep inspection is in use: install the FortiGate certificate on every phone and PC, or secure sites will not load.
  • Configure the VPN back to head office.
  • Confirm Facebook and YouTube are actually blocked — the one thing never yet tested.
