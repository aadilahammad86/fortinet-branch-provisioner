01

The job

Both ends of this VPN sit on dynamic ISP addresses, so neither can be reached by a fixed IP. Each side has to publish a name and look the other one up. HO already does its half — homadina.fortidyndns.com on WAN (port1). The branch has no name at all yet, which is why HO cannot dial it and the tunnel cannot exist.

So the two tabs are two halves of one task, and they are deliberately ordered that way in the window:

Tab 6 — Dynamic DNS

Register this branch's name with FortiGuard so its address is always findable, however often the ISP changes it.

Tab 7 — VPN Tunnel

Build the IPsec tunnel to HO's name, route the office LAN and Staff WiFi through it, and keep Guest out.

Both are on-site steps

FortiGuard DDNS only registers when the unit is online and registered with FortiCare — today every entitlement on the staged unit reads pending because it has never had an uplink. Neither tab can do its job during staging. They run after the ISP credentials go in, alongside the WAN cable.

02

Two names, two rules

The DNS name and the tunnel name are separate fields on separate tabs. They can read the same, but nothing forces it — a branch can be alain on the internet and abudhabi3 in the tunnel list. Each name has its own constraint, because each is limited by a different thing.

The tunnel name — capped at 11 characters

A FortiGate IPsec tunnel becomes an interface, and interface names stop at 15 characters; go over and the write is rejected. toHO costs four, so the branch name gets eleven and the maths can never fail:

you type · max 11alain fixedtoHO tunnel name · 9 of 15alaintoHO

The field enforces it by refusing the 12th character rather than complaining afterwards, and a live counter shows alain · 5/11 under the box. The tunnel name below it is shown but not editable — it is derived, so there is nothing to mistype.

Typed on the VPN tabTunnel nameLength
alainalaintoHO9
branch07branch07toHO12
musaffah11musaffah11toHO14
khalifacitykhalifacitytoHO15 — the ceiling

The DNS name — its own field, its own limit

Nothing about DNS cares about 15 characters, so this field is not squeezed by the tunnel's limit. It takes up to 24 characters — comfortably inside the 63 a DNS label allows, and short enough to type at a branch — so a site whose name will not fit in a tunnel name can still have a readable address on the internet.

Typed on the DNS tabRegistered nameTunnel name on the other tab
alainalain.fortidyndns.comcould be anything — say alaintoHO
khalifacitykhalifacity.fortidyndns.comkhalifacitytoHO — just fits
musaffah-branchmusaffah-branch.fortidyndns.comtoo long for a tunnel; use musaffahtoHO

Both fields take lowercase letters, digits and hyphens, not starting or ending with a hyphen — lowercase because one becomes a DNS name, and the same character set is safe in an interface name.

Kept apart on purpose

The tabs do not copy from each other, so changing one never silently rewrites the other. The VPN tab does show this branch's registered DNS name as a read-only reference line, since that is the thing HO needs — but it is information, not a link. If you later want one field driving both, that is a small change to make then.

Dynamic DNS tab

Four controls, one of which is usually left alone.

  This branch's name on the internet

  Branch name         [ alain_______________ ]  5 / 24
  Domain              [ fortidyndns.com  ▾ ]   matches head office

                      → alain.fortidyndns.com

  Internet port       [ wan1 ▾ ]        the port the ISP line plugs into

  [ ] This FortiGate sits behind an ISP router and gets a
      private address  (registers the public address instead)

  [ Check the name is free ]   [ Apply ]   [ Check it works ]

What each control does

ControlWritesNotes
Branch name + Domainddns-domainFull name including suffix, up to 24 characters before the dot. Suffixes offered: fortidyndns.com (default, matches HO), fortiddns.com, float-zone.com.
Internet portmonitor-interfaceDropdown of the device's real interfaces, WAN-role first, defaulting to wan1.
Behind an ISP routeruse-public-ipOff by default — matches your HO entry, whose Public IP column reads Disabled. On when the WAN port holds a private address.

The three buttons

  • Check the name is free — resolves the name from the laptop before claiming it. FortiGuard names are globally unique and only Fortinet Support can release one that is already taken, so this check is worth the two seconds.
  • Apply — writes the entry and reads it back.
  • Check it works — resolves the name again and compares the answer to the WAN address read off the device. Matching addresses is the only real proof it registered; a successful write proves nothing.
Why the laptop does the lookup

Registration happens between the FortiGate and FortiGuard, and the REST API exposes no status for it. An independent lookup from the laptop is the honest test — and it fails in the same way a branch user would experience it.

04

VPN Tunnel tab

The wizard in your screenshots asks for a dozen things across four steps. Most of them this tool already knows, so the form asks for four: this branch's name, HO's name, the key, and HO's networks. The reference line under the tunnel name shows what this branch registered on the DNS tab — the name HO will point at — without tying the two fields together.

  Tunnel name         alaintoHO        built for you · 9 of 15

  this branch is alain.fortidyndns.com on the internet

  Head office name    [ homadina.fortidyndns.com_____ ]
  Pre-shared key      [ ****************** ] [show]

  Ports
  Internet port out   [ wan1 ▾ ]     the tunnel leaves by this port
  Inside ports in     [x] internal   office LAN
                      [x] internal2  Staff WiFi
                      [ ] internal3  Guest WiFi — locked, guests never reach HO

  Networks
  This branch sends   172.21.0.0/21, 192.168.1.0/24   read from your tabs
  Head office has     [ 10.0.0.0/24________ ]  [+ add another]

  Internet access     stays local — branch traffic still goes out wan1

  [ Preview ]   [ Apply ]   [ Check tunnel ]

The two port pickers

These mirror the wizard exactly: the Internet port out is step 2's Outgoing Interface — the WAN the tunnel is built on. The Inside ports in are step 3's Local interface — the networks allowed to cross it. Both are real dropdowns reading the device's interface list, not hard-coded to wan1 and internal, so a branch wired differently still works.

Guest is rendered but permanently unticked, with the reason beside it. It is enforced in the package, not just greyed in the form — no code path can put internal3 into a selector or a policy.

What is deliberately not on the form

Encryption, DH groups, IKE version, DPD, keylife and NAT-traversal all have defaults chosen to match a FortiGate-to-FortiGate wizard tunnel. They sit behind an Advanced (match head office) expander, collapsed, because they only ever get touched when HO's settings differ — and then they must be edited, not discovered through a CLI session at a branch.

05

How the two ends find each other

Fortinet's documented pattern is one static side and one DDNS side. Yours has DDNS at both ends, which works, but it has one weak point worth designing around: after an ISP address change there is a DNS lag, and if a branch ISP hands out a CGNAT address the branch is not reachable from outside at all — HO could never dial in, no matter how correct the DDNS entry is.

So the design does not depend on HO dialling. Phase 2 gets auto-negotiate enable and keepalive enable, phase 1 gets dpd on-idle: the branch builds the tunnel itself, re-tries every five seconds until it is up, and keeps it up with no traffic. HO then simply finds a live tunnel waiting. The branch DDNS name stays useful for HO-initiated management and as the belt to that braces.

06

What gets written to the device

Every object the GUI wizard creates, written directly through the REST API and read back afterwards.

Dynamic DNS

PUT/POST /api/v2/cmdb/system/ddns 
// keyed by an integer ddnsid — reuse the entry on this
// interface if one exists, otherwise take max(ddnsid)+1
{
  "ddnsid": 1,
  "ddns-server": "FortiGuardDDNS",
  "ddns-domain": "alain.fortidyndns.com",
  "monitor-interface": [{ "interface-name": "wan1" }],
  "use-public-ip": "disable"
}

Tunnel — phase 1

POST /api/v2/cmdb/vpn.ipsec/phase1-interface 
{
  "name": "alaintoHO",          // becomes the tunnel interface
  "type": "ddns",
  "remotegw-ddns": "homadina.fortidyndns.com",
  "interface": "wan1",
  "ike-version": "2",           // must match HO
  "peertype": "any",
  "authmethod": "psk",
  "psksecret": "…",             // never logged, never saved
  "proposal": "aes256-sha256 aes128-sha256",
  "dhgrp": "14",
  "dpd": "on-idle",
  "dpd-retryinterval": 60,
  "nattraversal": "enable",
  "net-device": "disable",
  "wizard-type": "static-fortigate", // shows in the GUI as a wizard tunnel
  "comments": "Built by FortiGate Branch Provisioner"
}

Tunnel — phase 2, one selector per inside network

POST /api/v2/cmdb/vpn.ipsec/phase2-interface 
{
  "name": "alaintoHO-lan",
  "phase1name": "alaintoHO",
  "src-addr-type": "subnet", "src-subnet": "172.21.0.0 255.255.248.0",
  "dst-addr-type": "name",   "dst-name": "alaintoHO_remote",
  "auto-negotiate": "enable",   // the branch initiates
  "keepalive": "enable",        // and holds it up with no traffic
  "pfs": "enable", "dhgrp": "14"
}
// second selector: alaintoHO-staff, src 192.168.1.0/24

Addresses, policies, routes

ObjectNamedDetail
firewall/addressalaintoHO_local_lan, _local_staff, _remote_1…One per subnet on each side.
firewall/addrgrpalaintoHO_local, alaintoHO_remoteGroups so policies stay readable when subnets are added.
firewall/policyvpn_alaintoHO_outinternal + internal2 → alaintoHO, local group → remote group, NAT off.

router/static— blackholeSame subnet, blackhole enable, distance 254.
Why the blackhole route matters

It is the piece people leave out. Without it, when the tunnel drops, HO-bound traffic falls through to the default route and leaves the branch over the open internet — NATed, unencrypted and silently. With it, that traffic simply fails until the tunnel returns.

Every write is read back before the step reports success — the rule the rest of this codebase already runs on, since a FortiGate cmdb PUT can return success while quietly dropping a field it cannot apply.

The subnet-overlap check finally closes the open item in the project notes: unique addressing per branch stops being a convention and becomes something the tool refuses to violate.

08

Preview, Apply, Verify

Both tabs get the same three-verb treatment the existing tabs have, because it is what makes this safe to run at a branch with someone waiting.

  • Preview — reads the device and lists only what would change: "tunnel alaintoHO — would be created", "route 10.0.0.0/24 → alaintoHO — already correct". Sends nothing.
  • Apply — writes in dependency order (phase 1 → phase 2 → addresses → policies → routes), reading each back. A failure stops there and says which object it got to, so a re-run resumes cleanly. Every step is idempotent.
  • Check tunnel — reads /api/v2/monitor/vpn/ipsec and reports in plain words: up or down, how long, bytes each way, and which selector is dead if only one is. A down tunnel gets the three usual causes named — key mismatch, HO has no matching tunnel, no uplink yet — instead of a raw status code.

Templates and secrets

These fields join BranchSpec, so they travel in the saved branches built in v1.1. Pick Al Ain from the drop-down and the DDNS name, tunnel name, HO name, ports and subnets all fill in — the whole branch, including its tunnel, described by one file.

One observation worth acting on

HO's name is the same for every branch in the estate, and so is the encryption profile. Those belong in a small estate defaults file beside .env, filled in once and pre-loaded into every new branch, rather than retyped into each template where they can drift apart. The per-branch template still overrides it.

Duplicate branch subnets. Today every branch would use 192.168.1.0/24. medium Overlap is blocked, the shared default is warned about, and the saved branch records what each site actually uses.
The key is a real secret. Templates get emailed between laptops. medium Never written to a template, never printed to the log, masked in the form.
Reverses a recorded decision. The notes say the VPN is configured on-site and never scripted. low CLAUDE.md updated in the same commit, with the reason and the date.
13

Test plan

Written blind, so it gets proven on the bench before it goes near a branch. The staged 60F, an internet uplink, and HO's real tunnel at the other end.

  1. Back up the unit's config — the restore point for everything below.
  2. DDNS: apply, confirm system/ddns reads back, resolve the name from the laptop, compare to the WAN address.
  3. Apply a second time — must report "already correct" and change nothing.
  4. VPN Preview against a clean unit, then against a configured one: the second run must list zero changes.
  5. Apply, then check every object exists: phase 1, both selectors, four addresses, two groups, two policies, two routes including the blackhole.
  6. Confirm the tunnel comes up against HO and that a branch LAN machine reaches an HO machine.
  7. Confirm a Guest machine cannot — the test that matters most.
  8. Pull the WAN cable: traffic to HO must fail, not leak out of the internet connection. This proves the blackhole route.
  9. Save the branch, delete the tunnel, reload the branch, re-apply — identical result.
  10. Factory-reset rehearsal, as was done for the v1.0 checks.

15

Open decisions

The first three unblock phases 1 and 2; the rest have working defaults if you would rather not decide now.

1 · Head office networks

What subnet or subnets sit behind homadina.fortidyndns.com? The project notes propose 10.0.0.0/24. Whatever is real becomes the prefilled default.

2 · IKE version and encryption at HO

Open HO's existing tunnel and tell me IKE v1 or v2 and its proposals — the branch must match exactly. Default if unanswered: IKEv2, aes256-sha256 / aes128-sha256, DH 14.

3 · One pre-shared key for the estate, or one per branch?

Recommended: one per branch. A leaked key then costs one site, not all of them, and it is no extra work — the engineer types a key at each branch either way.

4 · "Incoming internet port" — which did you mean?

Planned reading: the wizard's two pickers — outgoing WAN port, and the inside ports allowed across the tunnel. The alternative is a second WAN for failover, so the tunnel moves to wan2 when wan1 dies. That is a real feature and a bigger one — SD-WAN or a second tunnel with route priorities — and I would treat it separately.

5 · Linking the two names later

They are independent for now, as you asked. Worth revisiting once a few branches are live: if in practice you always type the same word twice, one field with an override is less to get wrong. Leaving it separate costs nothing now and keeps that door open.

6 · Domain suffix

Default: fortidyndns.com, matching HO. The other two stay in the dropdown.

7 · Pre-shared key in saved templates

Recommended: never saved, matching the admin and PPPoE passwords. Say the word if convenience should win instead.
